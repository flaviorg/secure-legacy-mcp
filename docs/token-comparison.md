# Token comparison

Generated by `npm run bench:tokens` (`scripts/bench/measure-tool-tokens.ts --write`). Do not edit by hand: `npm test` compares this block and the README's against the meter's output (BEN-02).

## What is measured

Three ways to give a model access to the customer registry:

1. **REST mirror**: one tool per operation in `docs/legacy-api/openapi.json` (7 operations), generated by the pure function `openApiToMirrorTools` (`scripts/bench/mirror-tools.ts`): name from the `operationId`, description from `summary` and `description`, `inputSchema` from the `parameters` and the `requestBody`. Nobody wrote these definitions by hand, so nobody made them worse on purpose. There is no MCP server for the mirror: it would only echo the same definitions. Each call in the script goes straight to the API with `fetch`, and the measured result is the raw legacy body, which is what a pass-through tool would return.
2. **Business actions**: the 5 real tools, read by an SDK `Client` over `InMemoryTransport` connected to `createMcpServer`, with the service pointing at the in-process API. The measured result is the `content[0].text` of each call (compact JSON).
3. **Whole OpenAPI spec in the prompt**: minified `openapi.json`, the alternative without MCP.

Definitions are measured as `JSON.stringify` of the `{ name, description, inputSchema }` array, the three fields both tool variants have. In the scenarios, "argument tokens" is the sum of `JSON.stringify(args)` over each call (what the model has to generate) and "result tokens" is the sum of what comes back into the context. The tool name in each call is not counted on either side.

Tokenizer: `o200k_base` from `gpt-tokenizer` 4.0.0, offline, plus the characters/4 estimate (lesson 221522). Each run starts fresh APIs with SQLite `:memory:` and the 30-customer seed, one for the mirror and one for the business actions, so the C3 write on one side does not affect the other and two runs give the same output byte for byte (BEN-01).

## Scenarios

| Scenario | REST mirror | Business actions |
|---|---|---|
| C1 "phone of the customer with email X" | `getV1Customers {eml}` | `getCustomer {email}` |
| C2a "active enterprise customers registered in 2024" (fair comparison) | `getV1Customers {sts, seg, dt_de, dt_ate, lim: 10}` | `searchCustomers {status, segment, createdFrom, createdTo}` (default limit 10) |
| C2b same request, naive mirror | `getV1Customers {sts, seg, dt_de, dt_ate}` without `lim`, as a model could build it from the spec | same call as C2a |
| C3 "deactivate Teodoro" | `getV1Customers {nm}` and `putV1CustomersById` with the full object built from the previous result | `getCustomer {name}` and `deactivateCustomer {id}` |

The script is the minimal correct sequence, with no LLM and no model mistakes (`scripts/bench/scenarios.ts`).

## Caveats

- Other models tokenize differently. The absolute number changes from one provider to another; the relative comparison is what matters.
- Providers reformat the tool definitions before putting them in the prompt. The JSON measured here approximates what enters the context, not the billed value.
- The cost of the REST mirror's mistakes (the `A`/`I` and `1`/`2`/`3` codes, `cst_id` in the `PUT` body, which returns 500, listing everything without `lim`) is **not** included in the measurement. The exception is the C2b row, labeled as a model mistake. With the 30-customer seed only 3 rows match the filter, so C2b costs here almost the same as C2a; on a real table, without `lim`, the result grows with the registry.
- The business actions' JSON Schema uses the field helpers `emailField` and `isoDateField` (D-25), with a short `pattern`. The ADR `docs/adr/0001-business-actions-not-endpoint-mirror.md` records how much more the Zod 4 default (`z.email()` and `z.iso.date()`) would cost in the definitions.
- The published numbers are whatever the script produces. If the business actions cost more in definitions, the table shows it: the project trades richer descriptions (which help the model get it right the first time) for fewer calls and smaller results, with no cryptic fields for the model to decode.

The business action definitions cost 11% more tokens than the mirror's. With `outputSchema` and `annotations`, which the real `tools/list` also returns, the business actions add up to 2471 tokens (o200k); the generated mirror has no output schema.
